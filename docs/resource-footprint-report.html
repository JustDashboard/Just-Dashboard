1. Summary

Running Just Dashboard is genuinely lightweight — 110 MB of RAM and 9% of one core for all three containers. Installing or updating it is not: a cold build peaks at 2.07 GB of RAM, and because install and update are always docker compose up --build on the target machine, that build requirement — not the runtime — is what decides which servers can host it.

A 1 GB VPS can comfortably run the stack and cannot install it. That gap is the single most important finding here, and it is not mentioned in the README or checked by install.sh.

One fix has been applied since the first draft of this report, in §7: the image build no longer repeats the developer's type-check. That halves build wall time and takes ~320 MB off the peak, and it makes a 2 GB install stop failing intermittently — but it does not reach 1 GB, because a single Turbopack process needs 1.6 GB on its own and no setting in Next 16 reduces it.

Two background pollers dominate idle CPU, and both are larger than the metrics recorder people assume is responsible. The deployment Git watcher spawns a real git ls-remote against every watched project every 5 seconds (88 ms of CPU per call, 17,280 HTTPS calls per day per project), and the deployment queue runs two SQL statements every 250 ms whether or not anything is deploying. Stripped of those, the backend idles at 0.92% of a core instead of 8.14%.

Verified by direct measurement: per-container cgroup CPU and memory over a 288 s idle window and two load runs; a clean-room backend instance run from the extracted binary with its own data directory; 9,915 + 6,703 real HTTP requests; three timed cold starts; dbstat page accounting on a copy of the live 65 MB database; eleven cold frontend builds with process-tree memory sampling; a measured Go build stage; a byte-level comparison of the two build modes; a rebuilt and smoke-tested frontend image; layer-level image accounting; observed git subprocesses on the host.

Not tested, and why. The backend's authenticated API was not load-tested. Driving it needs the live admin password, and the account already carried failed_count=1 against a real lockout policy — a wrong guess would have locked the operator out of their own production dashboard. Backend figures below therefore cover its background work and unauthenticated surface, not authenticated API throughput. dockerd's own 14.45%-of-a-core draw could not be cleanly attributed to Just Dashboard without stopping the production stack, which I did not do. And the build floor in §6 is stated from measured process peaks rather than from pass/fail under emulated memory caps: os.cpus() ignores cgroup limits, so a capped build on this 8-core host still spawns seven workers and does not behave like the 1–2 vCPU machine it is meant to stand in for.

Nothing in docker-compose.yml caps it — there is no mem_limit, no cpus, and no deploy.resources on any of the three services.

Raising JD_METRICS_INTERVAL to 60 s cuts this by 4× and is the single most effective disk lever on a busy host.

One caveat on shrinking: the database runs with auto_vacuum=0 and prune() only issues DELETE, so the file never returns space to the filesystem. It plateaus at the 7-day high-water mark and reuses freed pages — correct behaviour, but lowering retention or removing containers later will not shrink the file without a manual VACUUM.

6. The build — the real constraint

There are no prebuilt images. Both install and update are git pull plus docker compose up --build (selfupdate/locate.go:13, selfupdate/install.go:18), so every machine that runs Just Dashboard must also compile it. I measured a cold frontend build — the memory-hungry half, and the one Docker always runs from scratch since .next never exists in the build context.

BuildWall timePeak single processPeak process tree
Cold, 7 workers (this 8-core host)47–49 s1.94 GB2.62 GB
Cold, 1 worker (a 1-vCPU VPS's shape)22 s1.57 GB2.07 GB
Backend Go stage44 s569 MB1.96 GB
Warm, Turbopack cache present9.5 s629 MB—

A correction to the first draft. The 2.56 GB figure I first reported was measured with 7 parallel page workers, because Next sizes workers from os.cpus() — and os.cpus() reports the host's core count, ignoring cgroup limits. A real 1–2 vCPU VPS spawns one worker, not seven. Re-measured in that shape the peak is 2.07 GB. The same blind spot makes cgroup emulation of a small VPS unreliable on this box, so the floor below is stated from measured peaks rather than from capped-build pass/fail.

The Go stage behaves well on small machines: its 1.96 GB aggregate is many parallel compiler processes, and the largest single one is only 569 MB, so it shrinks with core count. The frontend does not. Its 1.57 GB is one Turbopack process compiling the module graph, and that is the binding constraint on how small a server can install Just Dashboard.

Three ways to reduce it were measured and rejected. experimental.cpus: 1 changes the peak by under 2% — workers were never the driver. experimental.memoryBasedWorkersCount looks purpose-built for this but enforces a floor of four workers (build/index.js:374), so it cannot scale down. Building with --webpack and webpackMemoryOptimizations peaks at 2.28 GB and takes 113 s — the same memory, 2.3× slower. Next 16.3.5 exposes no Turbopack memory limit.

Build also leaves cache behind. Of 11.33 GB of BuildKit cache on this host, 4.96 GB across 29 records is attributable to Just Dashboard builds — the golang:1.26.8-bookworm, oven/bun:1 and node:22-bookworm-slim stages and the apt layers. It is reclaimable with docker builder prune, but nothing in the project prunes it, so it accumulates across updates.

7. What was changed

One change was applied and verified: the image build no longer repeats work that belongs to the developer. frontend/Dockerfile sets JD_IMAGE_BUILD=1, and next.config.ts reads it to skip the TypeScript pass and the prerender source maps. Nothing else was altered.

The reasoning is that next build runs tsc in a second Node process while the compiler still holds its own graph. That overlap, not the compile, is what pushed a 2 GB machine over the edge — and it did so intermittently, which is worse than failing cleanly. The code being compiled on an operator's server was already type-checked before release, so the check bought nothing there.

The developer gate is intact, and that was verified rather than assumed. A deliberately ill-typed file was added to src/: bun run build failed with TS2322: Type 'string' is not assignable to type 'number', and the same build with JD_IMAGE_BUILD=1 succeeded. The probe was removed. The consequence is documented in CONTRIBUTING.md: bun run build is now the only type-check, so an error missed there ships.

What this does not do is reach a 1 GB server. It removes the intermittent failure at 2 GB and halves the wait, but the 1.57 GB Turbopack process is untouched.

8. Server sizing — what this adds up to

ServerCan run itCan install/update itNotes
1 GB RAMYesNo110 MB for the stack is fine. The build peaks at 2.07 GB and one process of that is 1.57 GB, so no amount of swap or tuning fits it. Needs a prebuilt image.
2 GB RAMYesMarginal — add swap2.07 GB peak against ~1.9 GB available is right at the edge. The §7 change removed the second phase that made this fail intermittently, but swap is still the honest advice.
3–4 GB RAMYesYesComfortable for both, with room for the managed workloads.
1 vCPUYesYes, ~2–3 minIdle draw is ~9% of that core with a tab open, ~1% unattended. One worker rather than seven, which is also why the peak is lower than on this host.
Disk1.49 GB images + ~5 GB build cache + 322 MB data (growing per the model above). Plan for 10 GB free, not counting Docker itself or the workloads being managed.

Docker itself is a real part of the bill and is not counted above: dockerd holds 490 MB RSS and containerd 58 MB on this host, though that scales with the 15 containers running here and would be substantially smaller on a machine hosting only the dashboard.

The honest headline: as a running service Just Dashboard is lighter than most things it manages — 110 MB and a fraction of a core. The claim "runs on any server" holds for running it and breaks for installing it, and the fix is a distribution question (publish prebuilt images) rather than an optimisation one.

9. Known gaps — not fixed, flagged for a decision

  • No prebuilt images — still the decision with the most leverage. Every install and every in-app update compiles on the target machine, and after the §7 change that still peaks at 2.07 GB with a single 1.57 GB Turbopack process. Tuning cannot go lower; three approaches were measured and rejected. Publishing images to a registry would make the 1 GB tier viable and turn a weekly update from a minute of compiling into a pull. It needs a registry and a release job, which AGENTS.md says not to add unasked — so it is yours to call.
  • No resource limits in docker-compose.yml. No mem_limit, cpus or deploy.resources on any service. The frontend has been observed at 292 MB. On a 1 GB box, an unbounded Node process next to an unbounded root-equivalent backend is how the whole machine goes down rather than one container. Decide whether to cap them.
  • The Git watcher's 5-second interval is a const. GitWatchInterval in deploy/git_watch.go:15 is not configurable, costs 1.76% of a core per watched project, and makes 17,280 outbound HTTPS calls per project per day. Decide whether it becomes an environment variable, backs off when nothing changes, or stays as is.
  • The deployment queue polls every 250 ms when idle. engine.go:103 defaults PollEvery to 250 ms and the loop already has a wake channel for event-driven work. Decide whether the idle interval can be much longer given that wake-up exists.
  • No preflight and no documented requirements. install.sh checks for Docker but never checks RAM or free disk, and the README states no minimum. An install on a 1 GB box fails partway through a build rather than at a check. Decide the supported floor and assert it.
  • Build cache is never pruned. ~5 GB accumulates and nothing in the update path reclaims it.
  • Metrics default to the expensive end. 15 s × every container is the dominant DB cost. Worth deciding whether 30 s or 60 s should be the default, given charts are downsampled to at most a few hundred points anyway.
