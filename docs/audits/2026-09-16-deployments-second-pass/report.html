1. Summary

The Codex implementation of the first audit (F01–F09, part of R13) holds up, but the product still had two defects an operator hits on the first bad deploy: nobody was notified when a deployment failed, and a failed health check threw away the container's own logs before anyone could read them. Both are fixed and proven against a real backend on this server's Docker daemon.

Two further bugs surfaced only when the real product was driven end to end rather than through unit tests. Every restart of a deployment that has a readiness check ended as artifact_missing after the runtime had already been stopped and started. A concurrent SQLite writer, such as a notification being recorded or an operator saving settings while a worker ran, could kill the run with database is locked (517) and leave it as restart_evidence_missing. Both are fixed with regression tests.

Against Coolify, Dokploy and Vercel the deployment engine is now at parity on notifications (Discord, Slack, Telegram, e-mail, signed webhook), resource limits, failure diagnostics and a per-deployment console, and ahead on rollback fidelity, readiness-gated cutover and preview trust. It remains behind on build breadth (no PHP, Ruby, Java, Rust or .NET recipes), one-click templates, a full GitHub App flow, multi-server and teams. Those are scoped in section 7.

Verified working, on this machine: backend build, vet and all 33 test packages; the five-package deployment race gate run serially; frontend lint, type check, production build, 29 unit tests and all 107 Chromium tests against the production build; the live Docker activation fixture and the new live diagnoser fixture; and an isolated real-backend acceptance run (scripts/e2e-deployments.py) that deploys nginx with limits, deploys a crashing busybox image, restarts, and checks notifications, transcript, evidence and docker inspect at each step: 18 of 18 checks.

Security review of the touched surfaces

Provider and generic hooks compare raw-body HMACs in constant time and answer the same way for unknown ids and bad signatures; the preview frame's CSP restricts framing to the recorded origin and the dashboard; variable listing and reveal join environment to project in SQL; run logs check project membership. New surfaces follow the same rules: notification mutations and the enable/disable route require system.admin and a session and are audited; Discord and Slack webhook URLs and Telegram tokens are sealed and never returned; the commit-status poster validates repository, SHA, state and context before anything reaches gh's argv or a REST path. No new vulnerability was found in the reviewed code.

6. Not tested, and why

  • Real Discord, Slack, Telegram and SMTP delivery. No provider credentials exist in this environment. Payload shapes are tested through a rewriting transport and a captured mailer, and the signed-webhook kind was delivered for real in the acceptance run. Use Send test on each channel after configuring it.
  • A real GitHub commit status. Posting needs the dashboard's gh credential with write access to a repository; the poster is tested with a recorder. The first deployment of a GitHub-sourced project after this change will show just-dashboard/production on the commit.
  • The running dashboard was not rebuilt. The changes live in the worktree. The host is at 97% disk, and an image build that fails on disk space would affect every running container, so the rebuild is left for after space is reclaimed (see section 7).
  • Hosted CI. Nothing was pushed; the workflow gained the new live fixture and was checked locally with actionlint.
  • Public TLS, clean-host installation, ARM64, a 24-hour soak remain unverified, as in the first audit.

7. Known gaps — flagged for a decision

  • Rebuild the live dashboard. Decision: reclaim disk first (docker builder prune alone frees about 12.7 GB; the 43 GB of container writable layers deserve a look at which containers are writing where), then rebuild from Settings or with docker compose build && docker compose up -d. Rollback is the previous image tags.
  • Build breadth (B05). Rust, Java, .NET, Ruby and PHP have no automatic recipe; a Dockerfile still works. Decision: add native recipes one language at a time with locked live fixtures, or integrate Railpack or Nixpacks behind the same digest-pinning and secret-mount contract. The second is faster but hands base-image policy to a third party.
  • One-click templates (F10). The catalogue exists but deployment is refused by design until materialization, generated credentials and lifecycle are connected. Decision: which six templates ship first.
  • GitHub App and PR comments (R11). Commit statuses cover the commit view; preview URLs in pull requests need an App installation flow. Decision: whether to register a GitHub App for the product.
  • Native database backups (D8 of the plan). pg_dump, mysqldump, mongodump and S3-compatible destinations, wired into the coverage gate. Decision: scope of engines for the first release.
  • Multi-server and teams (R14, R15). Architectural work, not an extension of local Docker calls. Decision: whether the product stays single-server for 0.7.
  • Fleet p95 under parallel -race (D5). Ten statements per read is already fixed-cost; the budget fails only under contention from other race packages. Decision: keep serial CI (current) or profile the read model further.
  • Notification targets are unrestricted outbound URLs. Same trust boundary as every competitor; an administrator can point a webhook at any address. Decision: whether to refuse loopback and link-local targets for signed webhooks.
