1. Summary

The design system itself is in good shape — two purpose-built layout primitives (Panel, Page) and a shared state layer (state.tsx) are used consistently across all 17 routes, and the biggest historical anti-pattern this codebase used to have — every page hand-rolling its own Card — is fully gone: Card/CardHeader/CardContent have zero call sites left anywhere in src. That refactor finished.

What's left is smaller and more specific: a loading spinner that exists as a one-line component and is used in 32 places, but hand-duplicated as raw <Loader2 className="size-4 animate-spin"/> in 44 others; a status-pill component (StatusBadge, badge + dot + tone) used in 7 places, with the identical visual shape rebuilt by hand in 5 more, two of which (HealthBadge and the posture verdict badge) are the same 20-line tone switch copy-pasted between two files; a "clickable entity name in a table cell" pattern built fresh 13 times with no shared component at all; and three spots where a native <input type="checkbox"> quietly sits next to nine other files using the real Checkbox. None of this is a different design language competing with the system — it's the same visual result achieved by hand instead of by import, which is exactly the "different button doing the same job" pattern you asked me to check for.

I also went looking for the false positives — raw <button>, hardcoded hex colors, a native <select> — and confirmed four of them are deliberate, with reasoning already written into the code as comments. Those are called out below so they don't get "fixed" into something worse.

Verified by reading: every file under frontend/src that imports a UI primitive, plus a full-text grep across the tree for raw <button>, <input>, <select>, <table>, hex colors, Loader2, animate-spin, window.confirm/AlertDialog, and hand-rolled rounded-full border pill classes. Every finding below is a specific file:line, not an estimate.

2.2 Layout primitives — components/page.tsx

The frame every route renders into. Page sets the one measure (max-width 1600px), gutter and vertical rhythm for the whole app; fill is the variant for the terminal and log pages whose content is the viewport. PageHeader is the eyebrow/title/description/actions band at the top of every route. Section groups panels within a page that holds more than one idea (Appearance, Account, Certificates). Toolbar and SearchInput standardise the filter row that used to be assembled slightly differently on six pages. Metric/MetricStrip and DetailList/Detail replace the hand-rolled <dl> grids every card used to build with its own column widths.

2.3 Content primitive — components/panel.tsx

Panel is the single content block in the product — a framed surface with an optional tinted header strip (PanelHeader, with an icon tile, eyebrow, title, description, actions), an optional filter strip under it (PanelToolbar), a body (PanelBody, with flush for a full-bleed table and scroll for an internally-scrolling list), and a footer (PanelFooter). Well is the recessed surface for command output, diffs and stored secrets. This is the component that replaced shadcn's Card — see finding 3.8.

2.4 State primitive — components/state.tsx

Spinner, LoadingRows, LoadingPanel (skeleton with a heavier first row so the placeholder has the same silhouette as the table arriving), EmptyState, ErrorState (renders a missing module — no Docker socket, no systemd — as information rather than a failure), and Notice (a quiet banner for a fact the operator needs before acting, in four tones). Every one of these six is meant to be the single answer to its situation across the whole app; findings 3.1–3.2 are about the two that aren't yet.

2.5 Status vocabulary — components/status-dot.tsx

toneFor(state) maps every state vocabulary the backend speaks — Docker, systemd, pm2 — onto one four-value signal (running / stopped / warning / unknown). StatusDot is the small coloured dot; StatusBadge wraps it in a Badge with a label. Used across the docker, processes and system-users pages. Findings 3.1–3.2 are the places this exists in spirit but not in code.

2.6 shadcn/ui primitives — components/ui/

36 generated files. All are reached for consistently except one: card.tsx (0 call sites — see 3.8). Everything else — Button, Badge, Input, Select, Dialog (36 files), Sheet (3 files, for the genuinely slide-in cases — changelog, shortcuts), Tabs (16 files), Checkbox, Table, Tooltip, HoverCard, Popover, DropdownMenu, AlertDialog (used by exactly one consumer, ConfirmDialog — see 2.7), Accordion, Collapsible, Progress, Slider, RadioGroup, Switch, Toggle/ToggleGroup, Avatar, Breadcrumb, Command (⌘K palette) — is imported from its canonical file everywhere it's needed. Button's size scale (xs/sm/default/lg plus icon-xs/icon-sm/icon/icon-lg) is used correctly and consistently — there is no separate "small button" class anywhere.

2.7 Destructive actions — components/confirm-dialog.tsx

One dialog, two forms (plain confirm, and the same dialog with a typed phrase for the rare/unrecoverable routes), reached through a single confirm({ title, description, action, phrase? }) call exposed by a useConfirm hook. I grepped every call site of confirm( across the app (73 of them) and every AlertDialog import — there is exactly one AlertDialog consumer, this component. No page has rolled its own window.confirm() or a second confirmation dialog. This is the cleanest part of the system.

2.8 Theming

12 palettes (9 dark, 3 light) registered in lib/themes.ts, each with a matching [data-theme="<id>"] block in app/themes.css — that CSS file is the only place a colour value is defined. Switching is one attribute write on <html>, applied pre-paint by an inlined bootstrap script so there's no flash of the wrong palette. Two hand-named utility classes carry weight across the whole app: .eyebrow (the small-caps section label — 10px, tracked, uppercase, muted) and .numeric (tabular-nums, for any figure meant to be compared against its neighbour). Four custom CSS variables back the panel chrome everywhere: --surface-header, --surface-sunken, --hairline, --row-hover, all color-mix() against the active palette rather than fixed greys, which is what makes one Panel definition work unmodified across all 12 themes.

3.3 A "clickable entity name" table cell, built fresh 13 times

Every list page follows the same UX — the primary column of a table is a plain-looking, underline-on-hover button that opens the row's detail view — but there's no shared component for it, so the same three lines of Tailwind (truncate text-left text-[13px] font-medium hover:underline, occasionally wrapped in a max-w-[Nrem] min-w-0 div) are retyped per page:

app/(dashboard)/proxy/page.tsx:233, app/(dashboard)/processes/page.tsx:139,345, app/(dashboard)/git/page.tsx:149, app/(dashboard)/docker/page.tsx:418, components/proxy/streams-panel.tsx:125, components/docker/networks-tab.tsx:103, components/docker/images-tab.tsx:240, components/docker/volumes-tab.tsx:146, components/docker/stacks-tab.tsx:148, components/git/history-panel.tsx:99, components/database/query-tab.tsx:307, components/files/file-row.tsx:111.

Button's variant="link" doesn't fit — it colours the text primary and always underlines, and every one of these 13 wants default text colour with underline only on hover. A small RowLink/EntityLink component next to SearchInput in page.tsx (or a Panel sibling) would collapse all 13 into one import, and fix the one place they've already drifted apart: some wrap in max-w-[Nrem], some don't, and the max-width values themselves are inconsistent (18rem, 20rem, 22rem, 24rem, 26rem) with no evident reason tied to column width.

3.4 A "selectable list row" pattern, built fresh 4 times

The sidebar-style picker list — a vertical stack of buttons, each rounded-md px-2 py-1.5 text-left, selected state bg-primary/12 font-medium text-foreground vs. unselected text-muted-foreground hover:bg-[var(--row-hover)] hover:text-foreground — appears with matching classes in app/(dashboard)/logs/page.tsx:250-260 (log source list), components/database/redis-browser.tsx:224-236 (key list), components/database/browse-tab.tsx:457-470 (table list) and components/database/mongo-browser.tsx:251-263 (collection list). Same case as 3.3: not wrong anywhere, just the same 10 lines four times instead of once.

3.5 Checkbox: shared component in 10 files, native input in 3

Checkbox (Radix, components/ui/checkbox.tsx) is the established control — used in audit, system-users, files (×2), and four database components. Three files instead render a raw <input type="checkbox" className="size-3.5 accent-[var(--primary)]" />:

File:lineWhat it toggles
components/proxy/site-form.tsx:731"WebSockets on this path"

components/terminal/git-tools.tsx:535"Amend"

These three render with whatever the browser/OS draws for accent-color — a different shape and animation than the Radix Checkbox's square-with-check everywhere else. A user on Safari or Firefox will see a visibly different control on these three toggles than on the other ten.

3.6 Container limit inputs hand-roll Input's styling — and drop its focus ring

components/docker/container-detail.tsx never imports Input. Three raw <input> elements (the inline container-rename field at line 661, and the memory/CPU limit fields at 952 and 965) carry a hand-written class string — h-8 w-full rounded-md border bg-background px-2 text-xs outline-none focus-visible:border-ring — that's a subset of what Input actually applies. The part it's missing is focus-visible:ring-[3px] focus-visible:ring-ring/50: every other text field in the app gets a visible focus ring, these three get only a border-colour change, which is both a visual inconsistency and a (minor) accessibility regression for keyboard users on this one panel.

3.7 Progress bars: the shared component exists but is used twice

ui/progress.tsx (Radix) is imported in exactly two places (app/(dashboard)/page.tsx, app/(dashboard)/docker/page.tsx). Two more components draw their own percentage bar with an inline style={{ width: "N%" }} — components/stat-tile.tsx:63 (the meter under a stat figure) and app/(dashboard)/appearance/page.tsx:189 (the theme-swatch preview bar). Low priority: stat-tile.tsx is itself a single shared component reused everywhere a metric meter appears, so this isn't duplicated the way 3.1–3.5 are — it's one deliberate lighter-weight bar for a decorative sparkline-adjacent use, not competing with Progress. Worth a note, not urgent.

3.8 Card/CardHeader/CardContent/CardFooter: zero call sites

components/ui/card.tsx is fully generated shadcn boilerplate with no consumer anywhere in src — Panel replaced it completely, per the comment already in panel.tsx ("before this existed each page assembled its own out of Card/CardHeader/CardContent"). Not a bug, but dead code sitting in the primitives folder next to the thing that's supposed to be reached for instead — worth deleting in the 0.6.1 pass so nobody imports it out of habit while redesigning.

3.9 Terminal settings popover uses a native <select>

components/xterm-pane.tsx:1120 and :1134 (font family, cursor style, inside the terminal settings Popover) are plain HTML <select> elements, hand-styled to approximate the Radix Select used everywhere else in the app (17 files). This is the one finding in this section I'd flag as plausibly deliberate rather than confidently a gap — a Radix Select nested inside a Radix Popover is a real thing to get right (portal target, close-on-select interaction with the popover), and two two-to-three-option pickers in a tight settings panel is a defensible place to keep it simple. But it will visually read as the one native dropdown in an app that otherwise never shows one, so it's listed here rather than in the "confirmed intentional" section below — flagged for your call in section 5, not assumed.

4. Checked and confirmed intentional — not gaps

These matched the shape of a "different component doing the same job," but reading the code (and in two cases, the comment already sitting above it) confirmed they're deliberate. Listed so the redesign pass doesn't "fix" them into something worse.

  • Raw <button> for custom-shaped interactive elements (~55 occurrences). Tab pills, tree-row toggles, drag handles, chip close buttons, sidebar nav rows, HoverCardTrigger/DropdownMenuTrigger asChild wrappers, and the docker/git "term with a hover definition" pattern all use a bare <button> as a reset base for fully custom styling that Button's variant system doesn't (and shouldn't) cover. This is applied consistently everywhere it appears — it's the correct pattern for "this needs to be a real <button> element for accessibility, but look like a tree row / tab / chip / underlined term, not like a button" — not a gap.
  • Hardcoded hex colors in xterm-pane.tsx (~30 values, lines 77-102 and 664-667). The file's own comment explains it: xterm.js parses its theme colours itself and doesn't understand oklch() or CSS custom properties, so the terminal gets two hand-picked palettes (dark/light) that follow the active theme's mode rather than reading its tokens. This is the one legitimate escape hatch from "colour is defined only in themes.css" in the whole app, and it's already documented as such in the code.
  • docker/explain.tsx's Term/ExplainIcon mirrored by git/help.tsx's GitTerm/GitExplain. Two files, near-identical wrapper mechanics (a HoverCard around a dotted-underline button or a help icon). git/help.tsx's own top comment says this mirrors "the shape docker/explain.tsx established" on purpose, because each carries its own glossary content (Docker vocabulary vs. git vocabulary) and there was no third consumer yet to justify extracting a generic <TermHover glossary={} name={}>. Real, minor duplication (~20 lines), but deliberate — worth a shared helper only if a third feature grows its own glossary next.
  • No second confirmation system. Checked every confirm( call site (73) and every AlertDialog import — all roads lead to the one ConfirmDialog. No window.confirm(), no ad-hoc alert dialog anywhere.

5. What needs your call before I fix it

3.1, 3.5, 3.6 and 3.8 are pure substitutions with no design decision attached — same visual result, existing component, nothing to name or design. I'd fix those as part of 0.6.1 without further sign-off. The rest need a small decision each:

  • 3.2 (status pills). Do you want StatusBadge's tone vocabulary widened to include critical/notice so HealthBadge and the posture verdict badge can both become one shared component built on it — or a separate SeverityBadge sibling, since process state and health severity are genuinely different concepts that happen to look the same?
  • 3.3 / 3.4 (new shared components). These need a name and a home — e.g. RowLink and ListPicker in page.tsx/panel.tsx — before I migrate 17 call sites onto them.
  • 3.9 (terminal select). Leave as-is (nested-Radix-in-a-popover is a reasonable reason) or swap for Select?
